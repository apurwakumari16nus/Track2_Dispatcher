Part 1

How a chat message is guarded today

The LLM only reads the message. It never picks a workshop, does arithmetic or writes the final answer. Every step after it is plain Python that we can test and log.

1
Python

Message in

Empty text is rejected. Telegram only accepts chats on an allow list.

2
LLM

Reads it

Fills a strict JSON schema. The message is treated as data, never as instructions.

3
Python

Schema check

Strict validation, no extra keys. A broken reply becomes a named error, not a guess.

4
Python

Business rules

Order exists, one order matched, date, packing, eligibility, missing fields. Python sets the final behaviour and logs every rule.

5
Python

Answer

Fixed templates. A number check blocks any figure that did not come from a tool.

6
Dispatcher

Confirm

Nothing is saved until a person taps Confirm. Who and when go to the audit log.

The result in Sprint 2

30/30 correct behaviour on the evaluation set, 0 invented numbers, 15/16 on unseen requests. The design holds for normal messages. The gaps are in messages that are not normal.

Part 3

Stand-out additions, kept small

Each one is current practice in production LLM systems, fits in a few days, and stays inside the brief: tools do the maths, the LLM reads language.

GuardrailAbout 1 day

Grounding check

Every value the LLM returns must be traceable to words in the message. Anything else is dropped and asked about.

This is how production extraction systems catch hallucinated fields before they reach a decision.

Speed and costHalf a day

Prompt caching

The instructions, catalog and schema are identical on every call, so the provider can cache them. We report the response time change.

A cheap, measurable win that answers the "will it scale" question.

Data design1 to 2 days

Event log for batches

Each status change is appended, never overwritten. The current view is rebuilt from the log.

Same pattern as our audit log. Real systems use it because nothing is ever lost.

EvidenceDone

Guardrail check page

Every request run twice on the same model reply, guards off and on, with expected answers beside both. Type your own message to test.

Guards off reproduces the Sprint 2 replies exactly on all 62 recorded requests, so the comparison is fair.

Robustness1 to 2 days

Closure re-plan with a what-if

Before moving work, the simulator compares "move now" with "wait". The dispatcher sees both and decides.

Ties our robustness objective to a real decision instead of a chart.

Daily useHalf a day

Morning digest

One Telegram message each morning with what needs attention today.

How a busy owner actually wants information: pushed, short, at a fixed time.

What we will not do, and why

Multi-agent setupsOne reader plus exact tools is easier to test and already scores 30/30.
Fine-tuning a model30 labelled requests are far too few, and the brief rewards evidence over size.
Vector search or RAGOur data is small tables. Exact lookups beat similarity search here.
LLM arithmeticThe brief calls it the main source of wrong answers. Dates, costs and units stay in Python.
Part 4

Making it pleasant to use

Workshops cannot reply to us, so everything here works from data we already hold: the order book, the booked return dates and what the dispatcher records. The brief weighs usability over looks, so each idea saves a click or a question.

Home1 day

Today board

Three lanes on one screen: needs a decision, due back today or overdue, at risk of missing its date.

The first thing a dispatcher wants each morning, without opening four pages.

Tracking1 to 2 days

Due-back timeline

One row per workshop, a bar per batch from sent to due back, a line for today, overdue in red. Tap a bar to mark it received.

Shows the whole network's commitments at a glance, which a list of orders cannot.

Decision1 day

Pick against runner-up

The chosen workshop beside the next best: date back, spare days, cost and defect rate, with the one difference that decided it.

Answers "why not the other one?" before anyone asks, and makes overrides deliberate.

OverrideHalf a day

Reason chips

Overriding takes one tap on a reason: customer asked, quality concern, relationship, or a short note.

Fast enough that people actually log a reason, which is what makes the audit trail useful.

PaperworkHalf a day

Dispatch note

A printable note per confirmed batch: order, pieces, workshop, date back, approved by.

What actually travels with goods in a real workshop network, produced from the audit record.

Closures1 to 2 days

Closure re-plan

Mark a workshop closed, see its waiting batches with a suggested new home each, and confirm them in one go.

Turns our robustness objective into a two-minute task on a bad day.

Stay on Streamlit

It is Python, so the UI calls the same tested code as the evaluation. It deploys free to a public link, which the brief requires, and the team already knows it. A React rebuild would take most of the sprint and the brief gives UI 15% for usability, not the framework. Telegram stays as the chat channel, one way: the bot can push a morning digest to the boss without any workshop replying.

Why this order

What it adds up to

A full loop, not one step

Sprint 2 ends at "who gets this batch". Sprint 3 follows it until it comes back, which is the part the owner loses sleep over.

Safe with messy people

Real chats have typos, shorthand and several orders at once. The guardrails make the bot ask instead of guess.

Evidence we can defend

Frozen tests, a red-team set and a usability study give us numbers for Q&A, including where it still breaks.

Grading weights from the brief: problem solving 35%, engineering 20%, evaluation 15%, UI 15%, documentation 8%, presentation 7%. Owners to be set at the week 1 kickoff.
